# 0006. Доставка оповещений и повторная отправка

Предыдущий этап: [`0005-auth-and-users.md`](0005-auth-and-users.md). Термины: [`GLOSSARY.md`](../../GLOSSARY.md). Решение о ботах: [ADR 0001](../adr/0001-telegram-bot-per-user.md).

**Повод — инцидент:** проверка монитора закончилась таймаутом, но Оповещение в Telegram не пришло, хотя тестовое сообщение в канал доходило. Восстановить причину по данным нельзя:
- итог отправки хранится только в `last_delivery_*` Канала оповещения, и следующая отправка (в том числе тестовая) его затирает;
- нет Подключения Telegram → `send_alert` молча выходит;
- Оповещение отправляется один раз и при сбое теряется.

Возможна и другая причина: монитор уже был «упал» до таймаута, и тогда Оповещение не положено по правилам (план 0002, решение 9). Логи прода ещё не разобраны.

**Цель:** каждое Оповещение оставляет **Доставку оповещения** на каждый канал с ответом Telegram; недоставленное повторяется при следующих Проверках; сбой доставки виден на странице монитора и в списке мониторов.

**Вне объёма:** отдельный повторщик с нарастающими паузами; «проверить сейчас» (ещё не реализовано); дедупликация дублей после таймаута Telegram; каналы кроме Telegram.

## Принятые решения

| # | Решение |
|---|---------|
| 1 | Новый термин — **Доставка оповещения**: судьба одного Оповещения в одном Канале оповещения. Исходы: «не доставлено» (ожидает повтора, `pending`), «доставлено», «отменено» |
| 2 | Хранится: время первой и последней попытки, число попыток, текст последней ошибки (`description` Bot API или «Telegram не ответил вовремя»), `error_code` Telegram, `message_id` при успехе. Сырой JSON не хранится |
| 3 | Одна Доставка на пару «Оповещение × канал», а не запись на каждую попытку: промежуточные ошибки теряются, видны первая попытка, последняя ошибка и итог |
| 4 | Недоставленное повторяется при каждой следующей записанной Проверке монитора (успешной или нет), только в каналы, куда не дошло, без лимита попыток. Отдельного таймера нет: у монитора «раз в час» повтор будет через час |
| 5 | Повтор отправляет исходный текст (время падения прежнее) плюс строку «⚠️ Повторная попытка: первая не удалась ДД.ММ.ГГГГ ЧЧ:ММ:СС UTC» — с датой, потому что повтор может идти днями |
| 6 | Новое Оповещение монитора **вытесняет** его недоставленные: их Доставки → «отменено». «Упал» не дошёл, затем «восстановился» → уходит только «восстановился», в нём есть длительность простоя |
| 7 | Монитор без каналов — ничего не записывается. Каналы есть, но нет Подключения Telegram → Доставки «ожидает повтора» с причиной «нет Подключения Telegram», повтор продолжается |
| 8 | Отмена ожидающих Доставок: пауза монитора; изменение того, что проверяется (сброс в «неизвестно»); отвязка канала от монитора — только Доставки этого канала. Удаление канала удаляет его Доставки каскадом (вместе с историей доставок в него); отключение Telegram удаляет каналы, а с ними и Доставки. Блокировка пользователя ничего не отменяет: проверок нет, поэтому повторы ждут разблокировки |
| 9 | Срок хранения: Доставки уничтожаются через `HISTORY_RETENTION`, но ожидающие повтора — никогда. Поэтому Оповещение ссылается на монитор, а ссылка на породившую Проверку необязательна (`SET NULL`) |
| 10 | Результат тестового сообщения возвращается только в ответе на кнопку (ошибка Telegram — 502 `telegram_error`) и не хранится; при создании канала — в поле `test_message_error` ответа. `last_delivery_at/error` у канала удаляются; в списке каналов — последняя Доставка оповещения в этот канал |
| 11 | В истории монитора у Проверки, породившей Оповещение, — его Доставки по каналам. На странице монитора — плашка о Доставках, которые уже не удались (канал, ошибка, число попыток). В списке мониторов — значок у таких мониторов. Доставка без попыток (между записью Проверки и отправкой, после рестарта) — «ожидает первой попытки», сбоем не считается |
| 12 | Суперадмин видит Доставки на чужом мониторе так же, как владелец |
| 13 | Повтор выполняется в той же задаче, что и Проверка монитора, после её записи: проверки одного монитора не накладываются, поэтому повторы тоже |

## Шаг 1. Модель и миграция

- `alerts`: `id`, `monitor_id` (`CASCADE`), `check_id` (nullable, `SET NULL`), `kind` (`down`/`recovered`), `reason`, `down_since`, `created_at`. Текст собирается заново из этих полей и текущих названия и URL монитора: правка URL всё равно сбрасывает состояние и отменяет Оповещение (решение 8).
- `alert_deliveries`: `id`, `alert_id` (`CASCADE`), `channel_id` (`CASCADE`), `status` (`pending`/`delivered`/`cancelled`), `attempts`, `first_attempt_at`, `last_attempt_at`, `error`, `telegram_error_code`, `telegram_message_id`; уникальность `(alert_id, channel_id)`; индекс по `status`.
- Удаление `notification_channels.last_delivery_at`, `last_delivery_error`.
- `TelegramError` получает необязательный `error_code`; `send_message` возвращает `message_id`.

## Шаг 2. Отправка, повтор, вытеснение (backend)

`app/notifications/alerts.py`:
- `Scheduler._record` в той же транзакции создаёт `Alert` (если состояние сменилось и у монитора есть каналы, решение 7), отменяет ожидающие Доставки прежних Оповещений монитора (решение 6) и заводит Доставки `pending` на текущие каналы монитора.
- После записи Проверки — `deliver_pending(monitor_id)`: все `pending` Доставки монитора, по одной попытке на каждую; успех → `delivered` + `message_id`, ошибка → `attempts += 1`, `error`, `error_code`. Нет Подключения Telegram → попытка с этой причиной.
- Текст повтора — решение 5.
- Сбой одного канала не мешает остальным: сообщения уходят вне транзакции (`gather`), итог каждой Доставки пишется отдельным `UPDATE` по id. Канал или монитор, удалённый во время отправки, не откатывает итог остальных; отменённая во время отправки Доставка при неудаче остаётся «отменено», при успехе становится «доставлено».

Тесты (`httpx.MockTransport`): успех; ошибка Bot API с кодом; таймаут; повтор при следующей Проверке только в недоставленный канал; вытеснение «упал» → «восстановился»; нет Подключения Telegram → повтор после подключения; рестарт между созданием Доставки и отправкой — Доставка отправляется при следующей Проверке.

## Шаг 3. Отмена при паузе, правке, отвязке канала; срок хранения

- `pause`, `PUT` со сбросом состояния — отмена ожидающих Доставок монитора.
- `PUT` с изменённым списком каналов, удаление канала — отмена Доставок отвязанных каналов.
- `retention.py`: удаление Оповещений старше `HISTORY_RETENTION`, у которых нет ожидающих Доставок.

## Шаг 4. API

- `CheckOut` — необязательное `alert` с Доставками (канал, статус, попытки, ошибка, время).
- `MonitorOut` — `pending_deliveries`: список ожидающих Доставок (канал, вид Оповещения, ошибка, попытки, первая попытка); в списке мониторов — то же или счётчик.
- `NotificationChannelOut` — `last_delivery` (последняя Доставка оповещения в канал) вместо `last_delivery_*`.
- `POST /channels/{id}/test` — 200 при успехе, ошибка Telegram — 502 с текстом; в базу не пишет.
- Суперадмин — через существующие эндпоинты (решение 12).

## Шаг 5. Frontend

- `/monitors/[id]`: плашка ожидающих Доставок; в истории значок Оповещения у Проверки, по наведению/раскрытию — Доставки по каналам с ошибкой Telegram.
- `/` (список мониторов) и `/admin/users/[id]`: значок «оповещение не доставлено».
- `/channels`: последняя Доставка оповещения; результат теста — сообщением у кнопки.

## Шаг 6. Проверка готовности

| Сценарий | Ожидаемо |
|---|---|
| Бот удалён из чата, монитор падает | в истории «не доставлено: Forbidden: bot was kicked…», плашка на мониторе, значок в списке; Telegram-сообщения нет |
| Бот возвращён в чат | при следующей Проверке приходит «упал» с пометкой повтора, плашка исчезает |
| Бот удалён, монитор упал и восстановился | после возврата бота приходит только «восстановился»; «упал» — «отменено» |
| Пауза монитора с ожидающей Доставкой | Доставка «отменено», повторов нет |
| Тест канала | результат у кнопки; Доставки оповещений в канале не меняются |
| `docker compose restart backend` с ожидающей Доставкой | повтор при следующей Проверке |
| `make check` | зелёный |
