# 0002. Мониторы, проверки и оповещения в Telegram

Предыдущий этап: [`0001-scaffold.md`](0001-scaffold.md). Термины: [`GLOSSARY.md`](../../GLOSSARY.md).

**Цель:** пользователь создаёт **Монитор** через форму: URL, метод, заголовки, тело, **Ожидание**, периодичность и **Каналы оповещения**. Сервис по расписанию выполняет **Проверки**, ведёт **Состояние монитора** и шлёт **Оповещения** в Telegram-чаты, подключённые на отдельной странице.

**Вне объёма:** «проверить сейчас», аутентификация, шифрование секретов, порог из N неудач, Ожидание по regex или JSON, каналы кроме Telegram, Caddy.

## Принятые решения

| # | Решение |
|---|---------|
| 1 | Термины: Монитор (не «запрос»), Ожидание, Канал оповещения, Оповещение, Состояние монитора, Подключение Telegram — см. глоссарий |
| 2 | Цель Монитора — одно поле **URL**, схемы только `http`/`https` |
| 3 | Методы: GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS; по умолчанию GET |
| 4 | Заголовки — список пар «имя–значение»; тело — сырой текст, `Content-Type` задаёт пользователь заголовком; для GET/HEAD поле тела скрыто и не сохраняется. Всё хранится в SQLite открытым текстом |
| 5 | Ожидание по статусу — один точный код, по умолчанию 200 |
| 6 | Ожидание по телу необязательно: тело **содержит** подстроку (регистр учитывается). Читается не больше первого 1 МБ |
| 7 | HTTP-клиент: таймаут 10 с, редиректы **не** следуем, TLS проверяется. Таймаут и ошибка соединения — неуспешная Проверка |
| 8 | Периодичность — из списка 30 с / 1 / 5 / 15 мин / 1 ч, по умолчанию 5 мин |
| 9 | Оповещение — при смене Состояния монитора между «работает» и «упал», а также «неизвестно → упал». «Неизвестно → работает» и пауза — без Оповещения |
| 10 | Монитор ↔ Канал оповещения — многие-ко-многим; в форме множественный выбор, пустой допустим |
| 11 | Подключение Telegram — один бот на сервис; токен вводится на странице каналов, проверяется через `getMe` и хранится в БД |
| 12 | Канал появляется через автообнаружение: бота добавляют в чат → «Найти чаты» (`getUpdates`) → выбор чата, название → сохранение + тестовое сообщение. Обновления в Telegram живут 24 ч |
| 13 | Удаление Подключения или смена бота (другой `id` из `getMe`) — только после подтверждения; удаляет все Telegram-каналы. Повторный ввод токена того же бота сохраняет каналы |
| 14 | Удаление Канала разрешено и отвязывает его от Мониторов; подтверждение показывает, у скольких Мониторов он используется |
| 15 | Состояния монитора: неизвестно, работает, упал, на паузе. Упал — после 1 неудачи, восстановился — после 1 успеха. Возобновление → «неизвестно» |
| 16 | Правка URL, метода, заголовков, тела или Ожидания сбрасывает состояние в «неизвестно» и ставит Проверку на ближайший тик. Правка названия, периодичности или Каналов состояние не трогает |
| 17 | Оповещение о падении: название, метод + URL, причина, время. О восстановлении: название, URL, длительность простоя |
| 18 | Сбой `sendMessage` — лог, без повторов. У Канала хранится время и ошибка последней отправки, они видны в списке |
| 19 | SSRF: всегда запрещены loopback, link-local (включая `169.254.169.254`), unspecified, multicast, однокомпонентные имена (`backend`, `localhost`). Приватные сети (10/8, 172.16/12, 192.168/16, fc00::/7) — только при `ALLOW_PRIVATE_TARGETS=true` (по умолчанию `false`) |
| 20 | Аутентификации нет; в README — предупреждение не выставлять сервис в интернет без защиты |
| 21 | Объём UI: список Мониторов с состоянием; создание и редактирование одной формой; удаление; пауза/возобновление; страница Монитора с последними 50 Проверками; страница каналов. Название Монитора обязательно |
| 22 | Проверка хранит время старта, длительность (мс), код ответа (если был), успех, причину неуспеха. Тело ответа не хранится |
| 23 | Исполнитель: тик раз в секунду, берёт Мониторы с наступившим `next_check_at`, не больше 20 Проверок параллельно. `next_check_at` отсчитывается от **старта** Проверки |
| 24 | После рестарта просроченные Проверки выполняются сразу, по одной на Монитор, без «догоняющей» серии; сам рестарт Оповещений не порождает |
| 25 | Проверки старше 30 дней удаляет исполнитель раз в сутки |
| 26 | ADR не нужен: все решения обратимы и малозатратны |

## Шаг 1. Модели и миграция

Пакет `app/models/`, по модулю на агрегат; все модели наследуют `Base` из `app/db/base.py`.

- `Monitor`: `id`, `name`, `url`, `method`, `headers` (JSON — список `[имя, значение]`), `body` (nullable), `expected_status`, `expected_body` (nullable, подстрока), `interval_seconds`, `state` (`unknown`/`up`/`down`/`paused`), `state_changed_at`, `next_check_at` (nullable; `NULL` у Монитора на паузе), `created_at`, `updated_at`. Индекс по `next_check_at`.
- `Check`: `id`, `monitor_id` (FK, `ondelete=CASCADE`), `started_at`, `duration_ms`, `status_code` (nullable), `success`, `failure_reason` (nullable). Индекс `(monitor_id, started_at)`.
- `NotificationChannel`: `id`, `name`, `kind` (пока только `telegram`), `telegram_chat_id` (уникален), `last_delivery_at`, `last_delivery_error` (nullable).
- Связка `monitor_notification_channels` (`monitor_id`, `channel_id`, оба FK с `CASCADE`, составной PK).
- `TelegramConnection`: одна строка (`id = 1`, CHECK-ограничение) — `bot_token`, `bot_id`, `bot_username`, `updates_offset`.

Допустимые методы, интервалы и состояния — `enum.StrEnum` в `app/models/`, в БД хранятся строками.

`uv run alembic revision --autogenerate -m "monitors, checks, notification channels"`, ревизию проверить руками.

**Готово, когда:** `alembic upgrade head` и `alembic downgrade base` проходят на чистой БД; `ruff` чистый.

Коммит: `feat(backend): add monitor, check and notification channel models`.

## Шаг 2. SSRF-фильтр и API Мониторов

### 2.1. `app/monitoring/ssrf.py`

`async def resolve_target(url) -> None` бросает `ForbiddenTarget` с причиной:
- однокомпонентный хост — сразу отказ;
- литеральный IP проверяется напрямую, иначе все адреса из `getaddrinfo` (через `asyncio.get_running_loop().getaddrinfo`); отказ, если **хотя бы один** адрес запрещён (решение 19, `ipaddress`: `is_loopback`, `is_link_local`, `is_unspecified`, `is_multicast`, `is_private`).

`ALLOW_PRIVATE_TARGETS: bool = False` — поле `Settings`. Фильтр вызывается при сохранении Монитора (ошибка валидации 422) и перед каждой Проверкой (неуспешная Проверка с причиной «адрес запрещён: …»). Остаточный риск DNS-rebinding между резолвом и соединением в этом этапе принимаем; редиректы не следуем, поэтому через них фильтр не обойти.

### 2.2. Схемы и эндпоинты (`app/api/monitors.py`)

Pydantic-схемы `MonitorIn` / `MonitorOut`. Валидация: URL (`AnyHttpUrl`), метод, интервал и код (100–599) — из допустимых значений; `body` для GET/HEAD обнуляется; `channel_ids` должны существовать.

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/monitors` | список с состоянием и временем последней Проверки |
| POST | `/api/monitors` | создание; `state=unknown`, `next_check_at=now` |
| GET | `/api/monitors/{id}` | Монитор с `channel_ids` |
| PUT | `/api/monitors/{id}` | правка; сброс состояния по решению 16 |
| DELETE | `/api/monitors/{id}` | удаление вместе с Проверками |
| POST | `/api/monitors/{id}/pause` | `state=paused`, `next_check_at=NULL` |
| POST | `/api/monitors/{id}/resume` | `state=unknown`, `next_check_at=now` |
| GET | `/api/monitors/{id}/checks?limit=50` | последние Проверки, новые первыми |

### 2.3. Тесты

`tests/test_ssrf.py` (литералы, однокомпонентные имена, флаг приватных сетей, подмена `getaddrinfo`), `tests/test_monitors_api.py` (CRUD, валидация, сброс состояния при правке, пауза/возобновление). Общую фикстуру клиента с временной БД вынести в `tests/conftest.py`: тест создаёт схему через `Base.metadata.create_all`.

**Готово, когда:** `uv run pytest` и `ruff` зелёные.

Коммит: `feat(backend): add monitors API with SSRF guard`.

## Шаг 3. Исполнитель и Состояние монитора

### 3.1. Чистая логика (`app/monitoring/`)

- `expectation.py`: `evaluate(monitor, status_code, body_prefix) -> str | None` — `None` при успехе, иначе причина («ожидался 200, получен 503», «тело не содержит „ok“»).
- `state.py`: `transition(current_state, success) -> (new_state, alert)`, где `alert ∈ {None, "down", "recovered"}` по решениям 9 и 15.

### 3.2. Выполнение Проверки (`app/monitoring/runner.py`)

Один общий `httpx.AsyncClient(timeout=10, follow_redirects=False, verify=True)`, создаётся в `lifespan`. `run_check(monitor)`: SSRF-фильтр → `client.stream(...)` → чтение не больше 1 МБ → `evaluate`. Причины для таймаута и ошибок соединения: «таймаут 10 с», «ошибка соединения: …». Возвращает данные для `Check`.

### 3.3. Планировщик (`app/monitoring/scheduler.py`)

Задача `asyncio`, запускается в `lifespan` до `yield` и отменяется после:
- раз в секунду выбирает Мониторы с `next_check_at <= now` и сразу сдвигает им `next_check_at = now + interval`, чтобы следующий тик не взял их повторно (решения 23–24: просроченный после рестарта Монитор выполнится один раз);
- запускает `run_check` под `asyncio.Semaphore(20)`;
- по результату в одной транзакции пишет `Check`, применяет `transition` и обновляет `state`/`state_changed_at`; если Монитор за это время удалили, поставили на паузу или изменили (сброс по решению 16), результат отбрасывается;
- при `alert` вызывает отправку Оповещений (шаг 4); до шага 4 — заглушка с логом.

### 3.4. Тесты

`tests/test_expectation.py`, `tests/test_state.py` (все переходы из решений 9 и 15), `tests/test_runner.py` (`httpx.MockTransport`: успех, неверный код, тело без подстроки, таймаут, редирект как 301).

**Готово, когда:** тесты зелёные; локально Монитор на `https://example.com` раз в 30 с пишет Проверки (видно через `GET /api/monitors/{id}/checks`).

Коммит: `feat(backend): add background check scheduler`.

## Шаг 4. Подключение Telegram, Каналы и Оповещения

### 4.1. Клиент (`app/notifications/telegram.py`)

Тонкая обёртка над Bot API через `httpx`: `get_me`, `get_updates(offset)`, `send_message(chat_id, text)` (`parse_mode=HTML`, пользовательские строки экранируются). Запросы к `api.telegram.org` идут мимо SSRF-фильтра. Токен не попадает в логи: при логировании ошибок URL с токеном не выводится.

### 4.2. Эндпоинты

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/telegram` | `{connected, bot_username}`; токен не отдаётся |
| PUT | `/api/telegram` | `{token, confirm_replace?}` → `getMe`; неверный токен → 422; другой бот при существующих Telegram-каналах без `confirm_replace` → 409 с числом каналов |
| DELETE | `/api/telegram` | удаляет Подключение и все Telegram-каналы |
| POST | `/api/telegram/discover` | `getUpdates` с сохранённым `offset`; собирает чаты из `my_chat_member` и `message`, где бот — участник; возвращает `[{chat_id, title, type, connected}]` |
| GET | `/api/channels` | список с `monitors_count`, `last_delivery_at`, `last_delivery_error` |
| POST | `/api/channels` | `{name, telegram_chat_id}` → создание + тестовое сообщение |
| PATCH | `/api/channels/{id}` | переименование |
| DELETE | `/api/channels/{id}` | удаление, связи уходят каскадом |
| POST | `/api/channels/{id}/test` | тестовое сообщение |

Найденные в `discover` чаты, ещё не ставшие Каналами, хранятся только в ответе; `offset` двигается, поэтому найденный чат нужно сохранить сразу (в UI — одна страница).

### 4.3. Оповещения (`app/notifications/alerts.py`)

`send_alert(monitor, kind, reason, down_since)` — текст по решению 17. Каналы Монитора обходятся параллельно, для каждого обновляются `last_delivery_at` / `last_delivery_error`. Без Подключения Telegram — запись в лог и выход. Вызывается из планировщика вне транзакции записи Проверки.

### 4.4. Тесты

Telegram API подменяется через `httpx.MockTransport`: подключение и смена бота (409 / `confirm_replace`), `discover`, создание Канала с тестовым сообщением, текст Оповещений, запись ошибки доставки.

**Готово, когда:** тесты зелёные; с реальным ботом: подключение → бот добавлен в группу → «найти чаты» → Канал → тестовое сообщение пришло; Монитор на несуществующий хост присылает «упал», после исправления URL — сброс в «неизвестно» без Оповещения.

Коммит: `feat(backend): add Telegram notification channels and alerts`.

## Шаг 5. Страницы фронтенда

Все обращения к API — из `+page.server.ts` (form actions), как требует `AGENTS.md`. Общий хелпер `src/lib/server/api.ts`: `fetch` к `API_URL` с таймаутом; ошибки 422 и 409 превращаются в `fail(...)` с текстом для формы.

| Маршрут | Содержимое |
|---|---|
| `/` | таблица Мониторов: название, URL, Состояние монитора, последняя Проверка; кнопки «пауза»/«возобновить»; ссылка «создать» |
| `/monitors/new`, `/monitors/[id]/edit` | общий компонент формы: название, URL, метод, заголовки (добавить/удалить строку), тело (скрыто для GET/HEAD), ожидаемый код, необязательная подстрока тела, периодичность (select), Каналы оповещения (чекбоксы подключённых; если их нет — ссылка на `/channels`) |
| `/monitors/[id]` | параметры Монитора, его Состояние, последние 50 Проверок; «изменить», «удалить» |
| `/channels` | блок Подключения Telegram (ввод токена / `@бот` + «отключить»; при смене бота — повтор с подтверждением после 409); подсказка «добавьте бота в чат»; «найти чаты» → список с полем названия и кнопкой «подключить»; список Каналов с ошибкой последней отправки, «тест», «переименовать», «удалить» (подтверждение с числом Мониторов) |

Подтверждения удаления — через `confirm()` в `onsubmit`. Liveness переезжает из `/` в общий `+layout.server.ts` строкой в подвале. Стилизация минимальная.

**Готово, когда:** `npm run check`, `npm run lint`, `npm run build` без ошибок; сценарии из шага 4 проходятся через UI.

Коммит: `feat(frontend): add monitor and notification channel pages`.

## Шаг 8. Проверка готовности

| Проверка | Как |
|---|---|
| Миграции применяются в контейнере | `docker compose up --build -d`, в логах backend — `alembic upgrade head` без ошибок |
| Монитор работает | создать Монитор на `https://example.com`, 30 с → через минуту на его странице ≥ 2 успешные Проверки, состояние «работает» |
| Ожидание по телу | подстрока, которой нет в ответе → состояние «упал», причина «тело не содержит …» |
| Оповещения | при падении и восстановлении в Telegram-чат приходят оба сообщения |
| SSRF | Монитор на `http://localhost`, `http://backend:8000` или `http://169.254.169.254` не сохраняется |
| Пауза | на паузе новые Проверки не появляются; после возобновления — «неизвестно», затем Проверка |
| Рестарт | `docker compose restart backend` → состояния сохранены, лишних Оповещений нет |
| Удаление Канала | Канал исчезает из формы Монитора, Монитор продолжает работать |

Плюс зелёные `uv run pytest`, `uv run ruff check .`, `npm run check`, `npm run lint`.
