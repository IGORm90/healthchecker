# 0005. Вход через Telegram, Пользователи и Суперадмин

Предыдущий этап: [`0004-monitor-and-channel-management.md`](0004-monitor-and-channel-management.md). Термины: [`GLOSSARY.md`](../../GLOSSARY.md). Решение о ботах: [ADR 0001](../adr/0001-telegram-bot-per-user.md).

**Цель:** вход через Telegram OpenID Connect; **Пользователи** владеют своими Мониторами, Каналами оповещения и Подключением Telegram; **Суперадмин** видит всех пользователей, блокирует их, ставит их мониторы на паузу и смотрит историю их проверок.

**Вне объёма:** scope `telegram:bot_access` и оповещения в личку по `telegram_id`; удаление пользователей; лимиты; E2E-тесты.

## Принятые решения

| # | Решение |
|---|---------|
| 1 | Вход — Telegram OIDC (Authorization Code + PKCE S256). Client ID, Client Secret и redirect URI — в `.env` backend, во frontend секрета нет |
| 2 | Подключение Telegram у каждого Пользователя своё, не больше одного; `bot_id` уникален по сервису — чужой бот даёт ошибку поля «Этот бот уже подключён другим пользователем» (ADR 0001) |
| 3 | Каналы оповещения уникальны по паре `(user_id, telegram_chat_id)` |
| 4 | Регистрация открытая: первый вход создаёт Пользователя; повторный вход того же `sub` обновляет профиль |
| 5 | Суперадмин — Пользователь, чей `telegram_id` равен `SUPERADMIN_TELEGRAM_ID`. Флаг вычисляется при входе и хранится в Сессии: смена env действует со следующего входа |
| 6 | Сессия живёт 7 дней с момента входа, без продления; срок — константа. В базе — SHA-256 токена |
| 7 | Сессия хранит `build_id` сборки, в которой создана. Сессии другой сборки недействительны и удаляются при старте. `build_id` пишется в образ при `docker build` в слое после `COPY . .`: новая сборка с изменённым кодом — новый id, перезапуск контейнера — тот же. Вне Docker — `dev` |
| 8 | Миграция удаляет мониторы, проверки, каналы и Подключение Telegram: владельца у них нет |
| 9 | Блокировка пользователя — `blocked_at` у Пользователя. Блокировка удаляет его Сессии; вход заблокированного обновляет профиль, но Сессию не создаёт (`/login` с сообщением). Исполнитель пропускает его мониторы, их `state` не меняется. После разблокировки просроченные мониторы проверяются при ближайшем тике (их `next_check_at` уже в прошлом). Суперадмина заблокировать нельзя |
| 10 | Чужие ресурсы и `/api/admin/*` без прав — 404 |
| 11 | Суперадмину на чужом мониторе доступны просмотр, история проверок, пауза и возобновление — как владельцу. Правка, удаление и «проверить сейчас» — только владельцу. Владелец может возобновить монитор после паузы Суперадмина |
| 12 | Страницы Суперадмина: `/admin/users` (список, блокировка), `/admin/users/[id]` (мониторы пользователя с паузой). Чужой монитор открывается на обычной `/monitors/[id]` без «Изменить»/«Удалить» и с владельцем |
| 13 | JWKS Telegram загружается через общий `httpx`-клиент и кешируется в процессе; неизвестный `kid` — повторная загрузка. Так тесты подменяют Telegram через `httpx.MockTransport`, как и Bot API, без `respx` и `PyJWKClient` |
| 14 | Допустимые алгоритмы подписи `id_token` — `RS256` и `ES256`: `EdDSA` и `ES256K` в Telegram несовместимы со scope `profile` |
| 15 | `ORIGIN` frontend задаётся в `.env` (по умолчанию `http://localhost:3000`). Cookie `Secure`, если адрес страницы — https. Вход проверяется через HTTPS-туннель |
| 16 | Закрытые страницы — в группе `(app)`; без Пользователя — редирект на `/login`. 401 от backend внутри `(app)` — тоже редирект на `/login` |

## Шаг 1. Модели и миграция

- `pyjwt[crypto]` в зависимости.
- `core/config.py`: `TELEGRAM_CLIENT_ID`, `TELEGRAM_CLIENT_SECRET`, `TELEGRAM_REDIRECT_URI`, `SUPERADMIN_TELEGRAM_ID`, `BUILD_ID` (по умолчанию `dev`).
- `users`: `id`, `telegram_sub` (уникальный), `telegram_id` (уникальный), `name`, `username`, `photo_url`, `blocked_at`, `created_at`, `last_login_at`.
- `sessions`: `id`, `user_id`, `token_hash` (уникальный), `is_superadmin`, `build_id`, `created_at`, `expires_at`.
- `user_id` у `monitors`, `notification_channels`, `telegram_connection`; у Подключения Telegram — уникальные `user_id` и `bot_id`, синглтон убирается.
- Миграция `users_sessions_ownership` по решению 8.

## Шаг 2. Вход и Сессии (backend)

`app/auth/`: `telegram_oidc.py` (URL, PKCE, обмен кода, проверка `id_token`), `sessions.py` (создание, поиск, удаление, чистка), `deps.py` (`get_current_user` → Пользователь и флаг Суперадмина из Сессии, иначе 401), `router.py`:

| Эндпоинт | Что делает |
|---|---|
| `POST /api/auth/telegram/start` | URL авторизации, `state`, `code_verifier` |
| `POST /api/auth/telegram/callback` | обмен `code` + `code_verifier`, проверка `id_token`, Пользователь, Сессия → токен и срок; заблокированный — 403 `user_blocked` |
| `GET /api/auth/me` | текущий Пользователь и флаг Суперадмина |
| `POST /api/auth/logout` | удаляет текущую Сессию |

В `lifespan` — удаление Сессий чужой сборки и просроченных при старте, далее просроченных раз в сутки.

Тесты: своя пара RSA-ключей; корректный токен принят; чужая подпись, неверные `aud`, `iss`, истёкший `exp` отклонены; просроченная Сессия и Сессия другой сборки — 401; выход удаляет Сессию; повторный вход того же `sub` не создаёт второго Пользователя; заблокированный не получает Сессию.

Коммит: `feat(backend): sign in with Telegram OpenID Connect`.

## Шаг 3. Владение и права (backend)

- Все эндпоинты мониторов, каналов и Telegram требуют Пользователя и работают только с его записями; каналы в форме монитора — только свои.
- Решение 11: просмотр, история, пауза и возобновление — владелец или Суперадмин; `MonitorOut.user_id`.
- Исполнитель и `send_alert` — по Подключению Telegram владельца монитора; мониторы заблокированных пропускаются.
- Тесты изоляции пользователей и прав Суперадмина.

Коммит: `feat(backend): scope monitors and channels to users`.

## Шаг 4. API Суперадмина

| Эндпоинт | Что делает |
|---|---|
| `GET /api/admin/users` | Пользователи с числом мониторов и признаком Суперадмина |
| `GET /api/admin/users/{id}` | Пользователь |
| `GET /api/admin/users/{id}/monitors` | его мониторы |
| `POST /api/admin/users/{id}/block` / `unblock` | Блокировка пользователя (решение 9) |

Коммит: `feat(backend): add superadmin user management API`.

## Шаг 5. Вход (frontend), Docker

- `hooks.server.ts`: `handle` — cookie Сессии → `/api/auth/me` → `locals.user`; `handleFetch` — `Authorization: Bearer` к запросам на `API_URL`.
- `/login`, `/auth/login` (GET), `/auth/callback` (GET), `/auth/logout` (POST); временные cookie `state` и `code_verifier` — `HttpOnly`, `SameSite=Lax`, 10 минут.
- Страницы переезжают в `(app)`; в шапке — имя Пользователя и «Выйти».
- Docker: `ORIGIN` и `build_id` по решениям 7 и 15; `.env.example`.

Коммит: `feat(frontend): sign in with Telegram`.
